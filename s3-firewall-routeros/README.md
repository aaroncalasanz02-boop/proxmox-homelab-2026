# S3 — RouterOS firewall: deny-all policy between VLANs

MikroTik hAP ac lite · RouterOS 7.23.3 · VLANs 10 (OFFICE) / 20 (SERVERS) / 99 (MGMT)

After S2 the VLANs were isolated at L2 but the router forwarded freely between them:
any VLAN could reach any other. S3 replaces that with an explicit policy — **nothing
crosses the router, and nothing reaches the router, unless a rule allows it**.

pfSense was in the original plan and was dropped: the MikroTik already sits at the
one point every VLAN crosses, so adding a second firewall VM would only add a second
place to get the policy wrong.

> Real faults from this week are in [`TROUBLESHOOTING.md`](TROUBLESHOOTING.md).
> The generic "how to change a RouterOS firewall without locking yourself out"
> procedures are in [`../docs/runbooks-routeros.md`](../docs/runbooks-routeros.md).

---

## 1. Policy — who may reach what

| From | To | Allowed |
|---|---|---|
| MGMT (99) | any VLAN, Internet, the router itself | everything |
| OFFICE (10) | Internet | yes |
| OFFICE (10) | SERVERS (20) | **only the AD port set** (below) |
| OFFICE (10) | MGMT (99), the router's management services | no |
| SERVERS (20) | Internet | yes |
| SERVERS (20) | OFFICE / MGMT | **no** — servers answer, they never initiate |
| SERVERS (20) | the router (UDP 67) | yes — DHCP relay replies, see S4 |
| any LAN VLAN | the router: DNS (53), ICMP | yes |
| anything else | anything | **dropped by the last rule of each chain** |

AD port set (client → domain controller): TCP 53, 88, 135, 389, 445, 464, 636, 3268,
3269, 49152-65535 · UDP 53, 88, 123, 389, 464. That is DNS, Kerberos, RPC endpoint
mapper + dynamic range, LDAP / LDAPS / Global Catalog, SMB (SYSVOL), kpasswd and NTP —
the minimum a Windows client needs to join and log on to a domain.

Design intent in one sentence: **the management VLAN is the only place a
conversation with the router or with another VLAN can start; a compromised server
cannot pivot anywhere, and a compromised office PC can only talk to the DC on the
ports AD needs.**

## 2. How RouterOS evaluates a packet (why order matters)

Three filter chains, chosen by where the packet is going — decide this before writing
any rule:

| Chain | Traffic | Examples in this lab |
|---|---|---|
| `input` | **to** the router | WinBox/SSH to `.99.1`, DNS queries to the router, DHCP relay replies from the DCs |
| `forward` | **through** the router | VLAN 10 → VLAN 20, any VLAN → Internet |
| `output` | **generated by** the router | the router pinging or resolving DNS itself |

Rules are evaluated top-down and **the first match wins**. If nothing matches, the
default is *accept* — which is why a deny-all policy needs an explicit `drop` as the
last rule of each chain.

Connection tracking classifies every packet as `new`, `established`, `related` or
`invalid`. The policy is only decided on `new`; everything else is handled by two
rules at the top of each chain. Consequence: **there are no return rules**. Allowing
OFFICE → SERVERS:445 is enough; the replies come back as `established`.

## 3. The ruleset (17 rules, exported 2026-09-19)

Full file: [`../configs/mikrotik/firewall-filter.rsc`](../configs/mikrotik/firewall-filter.rsc).

### `input` — protecting the router

| # | Rule | Why |
|---|---|---|
| IN-1 | accept `established,related` | replies to conversations already allowed; no return rules needed anywhere |
| IN-2 | drop `invalid` | packets that belong to no known connection (broken TCP flags, orphan replies) |
| IN-4 | accept UDP 53 from `LAN` | the router is the DNS forwarder for VLAN 99 and the tunnel |
| IN-3 | accept TCP 8291,22,80 to `192.168.99.1` from `MGMT` | WinBox, SSH, WebFig — **only from the management list, only to the management IP** |
| IN-5 | accept TCP 53 from `LAN` | DNS over TCP (large answers, zone transfers) |
| IN-6b | accept UDP 13231 from `WAN` | WireGuard handshake (tunnel not documented yet) |
| IN-6 | accept ICMP from `LAN` | ping the gateway from any VLAN for diagnosis |
| IN-5b | accept UDP 67 from `SERVERS` | DHCP relay replies from the DCs — addressed to the router, so `input` (see S4) |
| IN-7 | **drop** | deny-all |

### `forward` — between VLANs and to the Internet

| # | Rule | Why |
|---|---|---|
| FW-1 | `fasttrack-connection` on `established,related` | established traffic skips the rest of the firewall; CPU stays near zero on this router |
| FW-2 | accept `established,related` | catches what fasttrack can't handle (its "backup") |
| FW-3 | drop `invalid` | packets belonging to no known connection |
| FW-4 | accept from `MGMT` | management (VLAN 99 + tunnel) reaches everything |
| FW-5 | accept `LAN` → `WAN` | every VLAN gets Internet |
| FW-6 | accept TCP 53,88,135,389,445,464,636,3268,3269,49152-65535 from `OFFICE` to `SERVERS` | the AD port set — domain join and logon |
| FW-7 | accept UDP 53,88,123,389,464 from `OFFICE` to `SERVERS` | the UDP half of the same set (DNS, Kerberos, NTP, LDAP ping, kpasswd) |
| FW-8 | **drop** | deny-all |

What the layout enforces without any explicit rule: SERVERS can't start anything
towards OFFICE or MGMT, OFFICE can't reach MGMT, and nobody outside `MGMT` can open
a management session — none of it is allowed above FW-8, so it dies there.

Conventions that came out of the faults of this week:

- **Address lists, not literal IPs.** `MGMT`, `SERVERS`, `OFFICE` are
  `/ip firewall address-list` entries; rules reference the list. Adding the second DC
  in S4 required editing one list entry, not hunting through rules.
- **Interface lists.** `LAN` = the three VLAN interfaces (+ the tunnel), `WAN` =
  `ether1`. Rules use the list, so topology changes don't rewrite rules. (Putting an
  interface in the wrong list is exactly how I locked myself out in S2.)
- **Every rule has a comment** (`IN-n` / `FW-n`) and rules are located by comment,
  never by number: RouterOS renumbers rules between a `print` and a `remove`.
- **Management accepts sit above the first drop** in both chains, so a mistake
  further down can never lock the admin out.
- **Interface names are case-sensitive and may contain spaces.** The VLAN interfaces
  here are `Vlan 10`, not `vlan10`; a rule referencing the wrong name doesn't error —
  it silently never matches.

Known wart: the comment labels are **not** in evaluation order — IN-4 sits above
IN-3, IN-5b below IN-6, after re-adds with `place-before`. Harmless here (no accept
shadows another), but the labels are names, not positions, and anyone reading the
comments as a sequence would reason wrongly about the policy. Renumbering is the
honest fix.

## 4. Bridge VLAN filtering — configured, **not enforced** (open finding)

The VLAN interfaces on this router hang off `bridge1`, not directly off the trunk
port `ether5`. Reason: the wifi radio. An access point is not a physical port you can
hang 802.1Q sub-interfaces from; it needs a bridge so its frames can be placed into a
VLAN. `wlan3` (SSID "Oficina") is configured as an untagged member of VLAN 10 with
`pvid=10`, so wireless office clients should land in the same segment as wired ones —
see the finding below on why that is not currently true.

Without `vlan-filtering` the bridge is transparent: it ignores tags and the PVID is
decorative — which is why the wifi "was in VLAN 10" but wasn't. With
`vlan-filtering=yes` the bridge only forwards the VLANs declared in
`/interface bridge vlan`. The table is populated and correct:

```routeros
/interface bridge port
add bridge=bridge1 interface=ether5                 # 802.1Q trunk to the Cisco
add bridge=bridge1 interface=wlan3 pvid=10          # wifi "Oficina" → VLAN 10
/interface bridge vlan
add bridge=bridge1 tagged=bridge1,ether5 untagged=wlan3 vlan-ids=10
add bridge=bridge1 tagged=bridge1,ether5 vlan-ids=20
add bridge=bridge1 tagged=bridge1,ether5 vlan-ids=99
add bridge=bridge1 tagged=bridge1,ether5 vlan-ids=30
```
Full export: [`../configs/mikrotik/bridge-vlan.rsc`](../configs/mikrotik/bridge-vlan.rsc).

**The export of 2026-09-19 shows `bridge1` without `vlan-filtering=yes`.** So the
table above is currently decorative: the L3 policy in §3 is fully in force (the
router's `Vlan` interfaces parse the 802.1Q tags themselves, which is why routing
and the firewall work), but the bridge does not police which VLAN a port may send,
and `pvid=10` on the wifi does nothing. Segmentation is enforced at the Cisco switch
and at L3; it is **not** enforced on the router's own bridge.

Two related findings in the same export:

- **The factory `bridge` still exists** next to `bridge1`, holding `ether2-4` plus
  `wlan1` and `wlan2` — a second, unsegmented L2 domain, including two wifi radios.
  Same "leftover default config" pattern that produced the stacked-firewall fault.
- **VLAN 30 is declared with no member port and no purpose.** Almost certainly
  residue from renumbering the VPN subnet 30.x → 40.x.

The detail that catches everyone: **`bridge1` must be listed as a tagged member of
each VLAN on itself**. That is what connects the bridge's VLAN sub-interfaces (the
router's own L3 legs, `.10.1 / .20.1 / .99.1`) to the VLANs — without it the router
loses its management IP the moment filtering is enabled.

Enabling it "crashed" the session twice. The table was correct both times. What
disappeared was the *management path*: I was connected through MAC-WinBox, which is
a Layer 2 protocol (MNDP) that bypasses the IP firewall and, once filtering was on,
arrived untagged, got the PVID applied, found no path and was dropped. The session
died, Safe Mode reverted the change, and it looked like the config was wrong.
Connecting by IP to `192.168.99.1` instead made the same change stick.

Native VLAN 999 on the trunk (anti VLAN-hopping, matching the Cisco side) only means
anything once filtering is on, and is applied as a **separate** change afterwards —
never in the same step as enabling filtering.

## 5. Verification — counters are the diagnostic tool

A rule is proven by its counter, not by reading it:

```routeros
/ip firewall filter print stats      # note the packet count of the rule you expect
<generate the traffic from the RIGHT host>
/ip firewall filter print stats      # compare
```

| What you see | Meaning |
|---|---|
| the expected accept goes up | the rule caught the packet — correct |
| the accept stays at 0 | not matching: wrong matcher, wrong order, or traffic never arrives |
| the final DENY goes up | the traffic dies there — an accept is missing above it |
| nothing in the whole chain moves | the traffic isn't entering where you think (wrong chain, wrong host) |

"From the right host" matters: a ping typed on the router's own terminal is `output`
traffic and will never move an `input` counter. Rules for `input` are tested from
another machine.

Tests run from the domain client on VLAN 10 (`192.168.10.15`) against the policy:

| Test | Expected | Result |
|---|---|---|
| `ping 192.168.10.1` (its gateway) | reply | ✅ |
| `ping 192.168.99.1` | reply (ICMP allowed to the router) | ✅ |
| WinBox / SSH to `192.168.99.1` | blocked (management only from MGMT) | ✅ — `IN-7` counter rises |
| `Test-NetConnection 192.168.20.10 -Port 389` | open (AD port set) | ✅ |
| `Test-NetConnection 192.168.99.20 -Port 8006` (Proxmox) | blocked | ✅ |
| `ipconfig /renew` | lease from a DC on VLAN 20 through the relay | ✅ — `IN-5b` counter rises |

## 6. What this week taught me

1. **First match wins — a firewall is an ordered list, not a collection.** An accept
   below the drop does not exist. For weeks the "real" policy sat under a leftover
   default-config drop and I only found out through counters.
2. **Counters don't lie.** Rule at 0 = not matching; deny rising = that's where the
   packet dies. First tool, before any hypothesis.
3. **RouterOS fails silently.** An empty `[find ...]` is a no-op with no error;
   `set src-address=""` doesn't clear a field (`set !src-address` does); a wrong
   interface name matches nothing. Verify with `print detail` after every change.
4. **Never delete by number.** Numbers are recalculated between `print` and `remove`.
   Delete by comment, and verify the `find` returns something first.
5. **One change, one variable.** Enabling VLAN filtering and changing the trunk PVID
   in the same step meant I couldn't tell which one broke the session.
6. **The management plane can hide a broken data plane.** MAC-WinBox kept working
   while the IP policy was inert, so nothing looked wrong.
7. **Check the software version before reading documentation.** The README said
   RouterOS 6.x; the device runs 7.23.3. Bridge VLAN handling and part of the
   firewall syntax changed between the two — hours were lost to v6 tutorials.
8. **Close one front before opening another.** Five open problems means no diagnosis
   is possible.
